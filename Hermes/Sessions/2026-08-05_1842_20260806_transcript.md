### **Hermes** · 2026-08-05 18:43 UTC

The memory layer isn't one file — it's a few coordinated pieces. Here's the map:

1. Built-in persistent memory (the `memory` tool — user profile + agent notes)
   - tools/memory_tool.py — the tool itself. File-backed, two stores (user.md and memory.md style entries), injected into the system prompt as a frozen snapshot at session start (preserves the prefix cache; mid-session writes go to disk but don't mutate the prompt).
   - Data lives in the profile-scoped dir: get_hermes_home() / "memories" → ~/.hermes/memories/ (or ~/.hermes/profiles/<name>/memories/ per profile). On this machine that's ~/.hermes/memories/, currently empty.
   - Intercepted at the agent level in run_agent.py before reaching handle_function_call().

2. Provider orchestration (external memory backends)
   - agent/memory_provider.py — the MemoryProvider ABC
   - agent/memory_manager.py — MemoryManager: add_provider, prefetch_all, sync_all, build_system_prompt, dynamic tool schema injection
   - plugins/memory/ — the provider plugins: honcho, mem0, supermemory, byterover, hindsight, holographic, openviking, retaindb (plus config_schema.py, query_rewrite.py)

3. CLI surface
   - hermes_cli/subcommands/memory.py — `hermes memory` (status / setup / reset)
   - hermes_cli/memory_setup.py — setup-wizard integration
   - hermes_cli/memory_oauth.py — OAuth for providers that need it

4. Related but distinct
   - hermes_state.py — SessionDB (SQLite): conversation history + FTS5 session search. This is the session store, not the memory layer, but it's the other long-term persistence piece.
   - gateway/memory_monitor.py — process-RAM monitoring for the gateway, unrelated to the memory layer.

If you're asking because you want to edit how memory works: the built-in store logic is tools/memory_tool.py, the provider abstraction is agent/memory_manager.py + agent/memory_provider.py, and the plugin surface is plugins/memory/. Want me to dig into any specific piece?
